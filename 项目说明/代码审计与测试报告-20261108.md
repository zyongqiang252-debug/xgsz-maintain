## 二、P0：匿名即可拿到管理员权限

### 2.1 钉钉扫码登录链可冒用任意账号（最严重）

**复现（全程不需要任何账号，3 个请求）**：

```bash
# 1) 匿名取 state
POST /api/v1/auth/dingtalk/scan/generate     {"redirect_uri": "http://127.0.0.1:18080/"}
# 2) 匿名回写身份 —— user_info 完全由调用方伪造
POST /api/v1/auth/dingtalk/scan/callback     {"state": "<上一步>", "user_info": {"userid": "atk", "name": "冒充", "mobile": "13800000000"}}
# 3) 匿名确认 —— 按 mobile 匹配到已有账号，直接下发 token
POST /api/v1/auth/dingtalk/scan/confirm/<state>  {}
```

**实测结果**：第 3 步返回 `username=admin role=ADMIN token=有`；用该 token 调 `POST /users/` 成功创建了一个新的 ADMIN 账号。

**根因**：
- `auth.py` 的 `dingtalk_scan_callback` 直接把请求体里的 `user_info` 当成钉钉返回的身份，没有校验来源
- `dingtalk_scan_confirm` 用 `mobile` 匹配系统账号后就 `_build_login_result(user)` 下发 JWT
- 三个接口都在 `DINGTALK_MOCK_MODE=true` 时才该可用，但**代码里没有对 Mock 模式做门禁**，真实模式同样接受伪造 `user_info`

**修复建议**：
1. `scan/callback` 只接受真实模式的 `code` 换身份；Mock 分支必须加 `if not settings.DINGTALK_MOCK_MODE: raise 403`
2. `scan/generate` 的 state 与浏览器会话绑定（一次一用 + 30s 过期 + HttpOnly cookie），confirm 时校验
3. 默认 `DINGTALK_MOCK_MODE=false`，Mock 页 `/dingtalk/mock-auth` 在非 Mock 模式下 404

### 2.2 验证码在响应里回显 → 任意账号改密

```bash
POST /api/v1/auth/send-code     {"phone": "13900000001", "scene": "reset_password"}
# -> 200 {"message":"验证码已发送","code":"123456","sms_enabled":false}
POST /api/v1/auth/reset-password {"phone":"13900000001","code":"123456","new_password":"xxx"}
# -> 200 密码重置成功
POST /api/v1/auth/login-by-password {"username":"13900000001","password":"xxx"}   # -> 200 token
```

**实测**：用 zhangwei 的手机号走完三步，拿到有效 token（测完已还原密码哈希）。admin 手机号同样在库里，`138****0000`，攻击者只要知道手机号就等价于拿到管理员。

**根因**：`send_sms_code` 在 `SMS_ENABLED=false` 时把固定码 `123456` 直接放进响应体（`"code": code`）。

**修复建议**：响应里永不返回 `code`；Mock 码只写日志；给 `send-code` 加 IP+手机号频控与图形验证码。

### 2.3 63 个接口没有鉴权依赖（占 148 个的 42%）

用 AST 扫描全部路由，函数签名里没有 `Depends(get_current_user)` / `require_*`，也没有函数体内手动校验的接口共 **63 个**。其中 6 个是登录注册类（应当公开），其余需要处理。

**已实测可利用的**：

| 接口 | 匿名实测 | 影响 |
|---|---|---|
| `POST /api/v1/knowledge/` | 200，写入成功（id=5） | **知识投毒**：往 RAG 里塞假知识，AI 回答会被污染 |
| `POST /api/v1/work-orders/{id}/complete` | 200，工单从 ARCHIVED 变成 COMPLETED | 任意改工单状态 |
| `POST /api/v1/upload/work-order-image` | 200，文件落盘 | 任意文件上传（见 P1-1） |
| `POST /api/v1/categories/` | 200，新增分类 | 字典被改，前端下拉跟着变 |
| `POST /api/v1/dingtalk/tech/start|complete/{id}` | 无鉴权 | 匿名推进他人工单 |
| `GET /api/v1/work-orders/{id}` | 200，返回真实故障描述 | 工单数据泄露 |
| `GET /api/v1/knowledge/{id}`、`/search`、`/solutions` | 200 | 知识库泄露 |
| `GET /api/v1/dingtalk/contacts`、`/departments`、`/sync-contacts` | 200 | 通讯录泄露 + 匿名触发同步 |

**修复建议**：
- 给 `work_orders`、`knowledge`、`categories`、`devices`、`fault_codes`、`search`、`upload`、`manual_codes`、`session` 这些 router 直接挂 `dependencies=[Depends(get_current_user)]`，再对个别公开接口单独放行
- 钉钉回调类（`event/callback`、`robot/callback`）保持无 Bearer 鉴权，但必须校验钉钉签名/Token
- 加一条 CI 检查：任何 `@router.*` 函数若同时缺鉴权依赖和 `# public: true` 标记就报错

## 五、已修复：Redis 缺失导致的接口慢 4~8 秒

**现象**：`GET /api/v1/spare-parts/alerts` 单次 4~8 秒，备件台账整页 **10.06 秒**，其余页面约 2.1 秒。

**根因**：`cache_service.client` 每次都重新 `redis.from_url(...).ping()`，连不上就 `_client=None`，**不记忆失败**；每次尝试等 2 秒连接超时。一个接口里 get+set 两次访问 ⇒ 4 秒起。

**修复**（`app/core/cache_service.py`）：失败后 60 秒冷却直接走内存缓存 + 连接超时降到 0.5 秒 + 日志去重。

**效果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `/spare-parts/alerts` | 4.02 ~ 8.04s | 0.00s |
| 备件台账页面 | 10.06s | **1.76s** |
| 驾驶舱 / 维修报表 / 导入页 | ~2.1s | **0.67 ~ 0.72s** |
| 27 项冒烟测试 | 27/27 | 27/27（无回归） |
